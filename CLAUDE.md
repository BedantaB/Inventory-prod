# Inventory app — working notes

Inventory, stock and orders for Indian wholesale businesses. Several completely separate shops
share one deployment; each has its own logins and data. Used by non-technical staff on low-end
Android phones (godown) and a desktop (counter). Full design: `docs/PLAN.md`.
Ideas not in scope go to `ROADMAP.md` — do not build unlisted features.

## Commands

```bash
pnpm dev               # http://localhost:3000
pnpm check             # typecheck + lint + unit/DB tests — run before every commit
pnpm typecheck         # next typegen && tsc --noEmit
pnpm lint
pnpm test              # Vitest (src/**/*.test.ts, tests/**/*.test.ts); DB tests use PGlite, no setup needed
pnpm e2e               # Playwright: builds, starts on :3100, runs phone + desktop (needs .env.local + seeded dev DB)
pnpm format

pnpm db:generate --name=<what_changed>   # after editing src/db/schema/*
pnpm db:generate --custom --name=<name>  # hand-written SQL migration (triggers, RLS, data)
pnpm db:migrate        # apply migrations to MIGRATION_DATABASE_URL
pnpm db:seed           # DEV ONLY: logins + sample data (add --reset to wipe business data first)
pnpm platform-admin:create  # production: create the platform admin login (ENV_FILE=.env.production.local)
# ENV_FILE=.env.production.local pnpm db:migrate   → migrate production (see DEPLOYMENT.md)
```

## Stack and versions to be aware of

- **Next.js 16.4** with `cacheComponents` + `partialPrefetching` on. APIs differ from older
  Next.js: read `node_modules/next/dist/docs/` before using a Next API. Learned so far:
  - Anything request-time (session, `searchParams`, `params`, DB reads) must render inside
    `<Suspense>`. Pages are sync, and an inner async component does the work.
  - `getSession()` calls `connection()` first, because Supabase reads the clock.
  - Suspense fallbacks must not read the URL either: no `usePathname`/`useSearchParams` in a
    fallback. Use static skeletons.
  - Middleware is `src/proxy.ts`. `error.tsx` receives `retry` (not `reset`).
  - Recently visited pages stay mounted but hidden (React `<Activity>`), so element ids must be
    unique per instance (`FormField` uses `useId`). In Playwright, wait for the new page's
    heading and use `.filter({ visible: true })` when a field also exists on the previous page.
  - Route props are typed with the global `PageProps<"/route">` / `LayoutProps<"/">`, which are
    generated by `next typegen` (part of `pnpm typecheck`).
- React 19.3, Tailwind 4, shadcn/ui (radix-nova), Zod 4, Drizzle 0.45 (postgres-js), Vitest 5,
  pnpm 12. Supabase keys use the new `sb_publishable_` / `sb_secret_` format.

## Layout

```
src/app/            routes only — thin files that call into features/
src/features/<x>/   one folder per feature: actions.ts (server actions), queries.ts,
                    schemas.ts (Zod, shared client+server), components/, *.test.ts
src/db/schema/      Drizzle tables, one file per area; index.ts re-exports
src/db/migrations/  generated + custom SQL — always committed, never edited after applying
src/db/seed/        seed script and sample data
src/lib/            shared helpers (money, qty, financial-year, env)
src/components/ui/  shadcn components
tests/db/           database rule tests (PGlite + real migrations)
e2e/                Playwright flows
```

## Patterns

- **Auth:**
  - `requireUser()` / `requireAdminPage()` come from `src/features/auth/session.ts`. They return
    the shop user, including `shopId`. `requirePlatformAdmin()` is for `/platform` pages and
    actions. `requireSignedIn()` accepts either kind of login (own password only).
  - Role checks use `can(user, permission)` from `src/features/auth/permissions.ts`.
  - The `(app)` layout also redirects signed-out or turned-off users, even on pages that load
    no data.
- **Server actions:**
  - Return `ActionResult` (`src/lib/forms.ts`): `success(key, vars)`, `failure(key)` or
    `fieldFailure(field, key)`.
  - Validate with `parseForm(schema, formData)`.
  - All messages are i18n keys.
- **Forms:**
  - `useServerForm(action, { schema, onSuccess })` (`src/components/form/use-server-form.ts`)
    gives inline validation with the same Zod schema, Enter-to-next-field, a loading state and
    toasts.
  - Build fields with `<FormField>` and `<SubmitButton>`.
  - Zod messages are i18n keys like `"validation.required"`.
- **"Add new" forms:**
  - Wrap them in `<FreshForm>` so they start empty after a save. Next keeps visited pages alive,
    so without it the saved values would still show.
- **Cart:**
  - The cart is a DRAFT order saved in the background (`useBackgroundSave` in `cart-editor.tsx`).
  - Checkout (`checkoutDraft` in `features/orders/data.ts`) is the only path to a completed
    order. It locks the draft and the item rows (id order) and rejects the whole order if
    anything is short.
- **Search pickers:** `<SearchCombobox>` is the shared search-as-you-type list (items,
  customers).
- **Choosing an item:** `<ItemPicker>` (search as you type, keyboard accessible), backed by
  `searchItemsAction`.
- **Destructive actions:** `<ConfirmAction>`.
- **Lists:** `<SearchBox>` (URL `?q=`), `<EmptyState>`, `<PageHeader>`.
- **Data access:**
  - Each feature has `data.ts` (functions taking `db: Database`, tested with PGlite in
    `tests/db/`) and `queries.ts` (server-only wrappers using `getDb()`).
  - Drizzle omits table names in single-table queries, so correlated subqueries must be
    written in plain SQL (see `listUnits`).
- **Lists:**
  - Search, filters and paging live in the URL (`src/lib/list-params.ts`): `<SearchBox>`,
    `<FilterSelect>`, `<Pagination>`, 20 rows per page from the server.
- **Photos:** resized on the phone (`compress-photo.ts`), stored in the private bucket, and
  served by `/photos/...` only to logins of the shop whose item uses the photo.
- **Text:** server components use `getMessages()`; client components use `useMessages()` /
  `useT()`.

## Rules that must not be broken

**Shops (multi-tenant)**

- Every business table has `shop_id` (`shopRef()` in `src/db/schema/columns.ts`). Every
  `data.ts` function takes `shopId` as its 2nd parameter, and every query filters on it,
  including updates and deletes. Pass `actor.shopId` from `requireUser()`; never take a shop id
  from the client.
- References between business tables are composite foreign keys `(shop_id, x_id) →
parent(shop_id, id)`, so the database rejects rows that mix shops. New tables follow the same
  pattern and add `unique (shop_id, id)` if other tables reference them.
- Names and numbers are unique **per shop** (SKUs, unit/category/brand names, order numbers,
  `order_counters`). Usernames are unique across all shops, because they are the login.
- One login = one shop. The platform admin (`profiles.is_platform_admin`, no `shop_id`) creates
  and turns shops on/off, and sees no shop data. A turned-off shop signs out all its logins.
- RLS policies use `current_shop_id()`. New shops get their units from
  `create_default_units(shop_id)`.
- `tests/db/shop-isolation.test.ts` covers this; extend it for every new table or data function.

**Money**

- Stored and calculated as whole **paise** (`bigint`, JS `number`). Never floats for money.
- Show money only via `formatINR()` (`src/lib/money.ts`) → `₹1,23,456.00`.
- Parse typed amounts with `rupeesToPaise()`.
- No GST anywhere for now (owner's decision; it's in ROADMAP).
- **Outstanding** = completed orders − payments not voided (`outstandingSql`,
  `customerBalance()` in `features/payments/data.ts`). Cancelled orders and voided payments never
  count; below zero = advance.
- Payments are never edited or deleted (IV007); the owner voids a wrong one (who, when, why).
  A payment with an `order_id` ("Paid now", written inside `checkoutDraft`) must match that
  order's customer and be on a completed order (IV008). Paid now ≤ order total.

**Quantities**

- `numeric(12,3)` in the DB, returned as strings. In TS use milli-units via `src/lib/qty.ts`
  (`qtyFromDb`, `qtyToDb`, `parseQty`, `formatQty`, `lineTotalPaise`). Never `parseFloat`.
- Decimals are allowed only when the item's unit has `allows_decimal` (kg, litre).

**Stock**

- `items.current_stock` and `items.avg_cost_paise` change **only** by inserting a
  `stock_movements` row. The DB trigger `apply_stock_movement` updates the item, and a guard
  trigger rejects any other change (error IV001). Don't try to update them directly.
- Stock-in (IN) needs `unit_cost_paise` and `stock_entry_id`. The weighted average cost is
  recalculated by the trigger.
- Stock-out (OUT) needs `unit_price_paise` and `order_id`. The trigger records the average cost.
- Correct stock (ADJUST, owner) needs a `reason` (`adjust_reason`; OTHER also needs a `note`).
  The trigger records the average cost and leaves it unchanged. Use `correctStock()`.
- RETURN puts stock back from a **cancelled** order, at the cost recorded on the sale (IV006
  otherwise). Only `cancelOrder()` writes them.
- Order ledger rows by `seq`, not by `created_at`: rows written in one transaction share
  `created_at`.
- `stock_movements` rows are immutable (IV003). Completed orders are immutable except
  `archived_at` and the one-way change to CANCELLED (with `cancelled_at/_by`, `cancel_reason`).
  Cancelled orders are immutable too (IV004).
- Sales totals count `status = 'COMPLETED'` only. Lists and history show cancelled orders,
  marked; drafts never.
- Enum values added in a migration can't be used in the same transaction (all pending
  migrations run in one). Compare enums as `::text` in CHECKs and SQL in such migrations.
- Map DB errors with `getPgErrorCode()` + `DB_ERROR` (`src/db/errors.ts`).

**Server is the source of truth**

- All writes go through Server Actions.
- Recalculate prices, totals and stock on the server from DB values; never trust client numbers.
- Every server action starts with an auth check (logged in + `profiles.is_active`) and a role check.
- **STAFF cannot:** manage users, change an existing item's selling price, archive anything.
  **STAFF can:** set a price when creating an item, and set the selling price per order line.

**Database connection**

- Supabase's pooler needs `prepare: false` and `max_pipeline: 1` (`src/db/create.ts`).
- With pipelining on, a page running several queries at once stalls forever with no error
  (it happened on the dashboard). Don't remove it.

**Security**

- RLS is enabled on every table. Policies allow SELECT for active logged-in users only, with
  no write policies.
- The app connects as the table owner via `DATABASE_URL`, so RLS doesn't apply to it. That is
  why the server-side checks above are mandatory.
- Any new table must enable RLS in its migration; `tests/db/security.test.ts` fails otherwise.
- Secrets only in `.env.local` (gitignored). `SUPABASE_SECRET_KEY` and `src/db/index.ts` are
  server-only.

**Data conventions**

- Tables have `id uuid`, `created_at`, `updated_at` (DB trigger), `created_by`.
- Soft delete via `archived_at`; nothing is hard-deleted except discarded draft orders.
- Exception: `stock_movements` has no `updated_at`/`archived_at` because it is a ledger.
- Items: show names with `itemDisplayName()` ("Permanent Marker – Blue"). Each colour or variant
  is its own item.
- Items: MRP is optional, and selling price ≤ MRP (Zod + DB check).
- "Vendors" in code/DB are the businesses we **sell to**; the UI calls them **Customers**.
- Order numbers: `ORD-<financial year>-00001` (`src/lib/financial-year.ts`), gapless per FY via
  `order_counters`.
- Business dates use `Asia/Kolkata`.
- Staff log in with a username mapped to `username@STAFF_EMAIL_DOMAIN`
  (`src/features/users/login-identity.ts`). The admin uses a real email.

**UI**

- Plain words ("Add Stock", "New Order", "Customers"), no jargon. All UI text lives in
  `src/i18n/` (Hindi will be added later) — no hard-coded strings in components.
- Mobile first:
  - min 44px tap targets, large fonts, high contrast, one clear primary button per screen
  - bottom nav on mobile, sidebar on desktop
  - `inputMode="decimal"`/`"numeric"` on number fields
- Every action shows a loading state, a success toast and a friendly error that says what to do.
  Confirm before destructive actions. Empty states invite the first action.
- Lists: search box first, filtering as you type (debounced URL params), server-side pagination.
- Keep client bundles small: Server Components by default, `"use client"` only where needed.

## Workflow

- Work in phases (see `docs/PLAN.md`). Stop after each phase for the owner to review.
- Before committing: `pnpm check`. If schema changed: `pnpm db:generate` and commit the migration.
